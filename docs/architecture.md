# 《软洋羊》微信小程序架构设计

## 1. 产品与架构目标

《软洋羊》是一款以领养、互动、喂养和陪伴为核心的电子宠物产品。首期围绕“养成闭环”建设：领养宠物 → 日常互动与喂食 → 获得成长和亲密度 → 签到、完成任务并领取奖励 → 与宠物聊天。

架构目标：

- 先支持单用户、单只主宠物的轻量 MVP，同时避免把“单宠物”写死在数据结构中。
- 宠物属性、资源扣减、成长、奖励和签到结果以服务端为准，客户端不直接决定奖励。
- 将互动、养成、任务、签到、聊天拆分为清晰的页面与业务域。
- 通过 API 和数据模型预留多宠物、换装、活动及广告变现能力。
- AI 能力经由自有服务端接入，客户端不保存模型供应商密钥。

## 2. 技术边界与运行形态

建议首期采用：

- **客户端：** 原生微信小程序，TypeScript、WXML、WXSS；使用微信小程序标准页面、组件和分包机制。
- **服务端：** 独立业务 API（可部署在云托管或常规云服务），负责身份校验、养成规则、奖励结算、AI 代理及数据持久化。
- **数据库：** 关系型数据库作为用户、宠物和交易事实的主存储；必要时增加缓存、队列及对象存储。
- **AI 服务：** 服务端统一封装模型调用、配额、内容安全检查和超时处理。

客户端通过 `src/services` 调用业务 API，不直接访问数据库或第三方 AI。若首期选择微信云开发，可将云函数视为服务端 API 的部署形态；业务边界和数据所有权保持不变，避免页面直接耦合云数据库。

### 目录约束

- `pages` 只负责编排页面交互，不在页面内实现奖励、升级等权威规则。
- `components` 只承载可复用 UI，不自行请求或修改全局业务数据。
- `domain` 放可测试的展示映射、枚举和客户端非权威规则；服务端仍负责最终业务校验。
- `services` 管理 API 边界，统一处理登录态、错误码、超时和请求追踪。
- 页面导航、Tab 配置和分包声明统一维护在 `app.json`。
- 仅把可恢复的轻量信息（如非敏感 UI 偏好）放本地缓存；不要用本地缓存替代服务端事实。

## 4. 页面结构与导航

### 4.1 主导航

推荐底部 Tab：

1. **牧场（首页）**：宠物展示、状态、互动、喂食、亲密度/成长摘要。
2. **任务**：每日任务、成长任务、进度与奖励领取。
3. **聊天**：与宠物进行 AI 对话。
4. **我的**：用户资料、签到入口、设置、隐私与帮助。

签到可以从首页展示每日入口并跳转到签到页；如果签到是核心日活目标，也可将其作为任务页中的显著模块，而不必单独占用 Tab。

### 4.2 页面职责

| 页面 | 主要职责 | 关键交互 |
|---|---|---|
| `pages/home` | 展示当前宠物、成长阶段、亲密度、可用资源和待办提示 | 点击互动、选择食物喂养、进入宠物详情、签到入口 |
| `pages/adopt` | 新用户首次创建宠物 | 选择外观/名字、确认领养；成功后进入牧场 |
| `pages/pet-profile` | 展示宠物资料、成长记录和属性说明 | 查看等级、经验、亲密度及事件记录 |
| `pages/tasks` | 展示任务、进度和奖励状态 | 查看任务、领取可领奖励 |
| `pages/check-in` | 展示今日签到状态、连续签到/累计签到信息 | 签到、查看奖励和历史 |
| `pages/chat` | 展示会话与聊天记录 | 发送消息、重试、加载历史 |
| `pages/inventory` | 展示食物与道具数量 | 选择物品并触发喂食；可作为首页半屏面板实现 |
| `pages/profile` | 用户设置、账号与产品信息 | 隐私授权管理、反馈、退出/清除本地会话 |

### 4.3 关键页面状态

页面统一考虑 `loading`、`success`、`empty`、`error` 和 `offline/stale` 状态。喂食、签到、领取奖励等会改变服务端数据的操作应防止重复点击；成功后用接口返回的新状态刷新相关视图，而不是仅在本地累加数值。

## 5. 数据模型设计

### 5.1 通用约定

- 所有业务记录使用不可预测的主键；服务端内部可使用数据库主键，但对外 API 使用稳定 ID。
- 业务表含 `created_at`、`updated_at`；软删除仅用于有恢复/审计需求的数据。
- 用户隔离通过服务端认证上下文确定，不能信任客户端传入的 `user_id`。
- 时间戳统一存储 UTC；签到“自然日”按产品配置的业务时区计算，记录结算日期，避免客户端时区变化影响奖励。
- 经验、亲密度、资源变更由服务端规则计算；关键奖励写入流水并保持可追溯。

### 5.2 核心实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| `User` | `id`、`wx_openid`（或身份映射 ID）、`status`、`timezone`、`created_at` | 用户主档。微信身份标识只保存在服务端；客户端以登录态访问业务 API。 |
| `Pet` | `id`、`owner_id`、`name`、`species`、`level`、`experience`、`affection`、`growth_stage`、`state_version`、`created_at` | 宠物核心档案。首期每用户一只主宠，但数据关系允许未来一对多。`state_version` 可用于并发更新控制。 |
| `PetState`（可选） | `pet_id`、`hunger`、`mood`、`last_interacted_at`、`updated_at` | 仅当饥饿、心情等动态状态确实参与玩法时引入；不要为未定义的属性提前增加复杂度。 |
| `UserResource` | `user_id`、`resource_type`、`balance`、`updated_at` | 可用于金币、饲料券等可消耗资源。若 MVP 只有食物数量，可先由库存承担，不必建立通用货币系统。 |
| `InventoryItem` | `id`、`user_id`、`item_type`、`item_config_id`、`quantity`、`updated_at` | 用户持有的食物或道具数量。对外展示由配置表补充名称、图标和使用规则。 |
| `ItemConfig` | `id`、`type`、`name`、`effect_config`、`enabled`、`version` | 服务端维护的物品规则配置；客户端仅展示可公开的配置。 |
| `PetInteraction` | `id`、`user_id`、`pet_id`、`interaction_type`、`result`、`created_at` | 互动事件记录，可用于限频、任务进度、行为分析与问题追踪。按保留周期控制数据量。 |
| `DailyCheckIn` | `id`、`user_id`、`business_date`、`streak_snapshot`、`reward_id`、`created_at` | 每用户每业务日期最多一条；对 `(user_id, business_date)` 建唯一约束，保证签到幂等。 |
| `TaskDefinition` | `id`、`task_key`、`period_type`、`target_count`、`reward_config`、`valid_from`、`valid_to`、`enabled`、`version` | 任务模板/活动配置。规则版本化，避免调整配置后历史任务解释不一致。 |
| `UserTaskProgress` | `id`、`user_id`、`task_definition_id`、`period_key`、`progress`、`status`、`completed_at`、`claimed_at` | 用户在某任务周期内的进度及领取状态；`period_key` 表示日期或活动周期。 |
| `RewardLedger` | `id`、`user_id`、`source_type`、`source_id`、`reward_payload`、`idempotency_key`、`created_at` | 奖励发放流水。对幂等键设唯一约束，防止重复领取、重试重复入账。 |
| `ChatConversation` | `id`、`user_id`、`pet_id`、`created_at`、`updated_at` | 一段宠物聊天会话。 |
| `ChatMessage` | `id`、`conversation_id`、`role`、`content`（或安全存储引用）、`status`、`created_at` | 聊天消息；限制内容大小和保留期限，明确告知用户数据用途。 |

### 5.3 关系与约束

- `User 1—N Pet`；首期通过业务规则限定一个活动主宠物，不把数据库关系限制为永久一对一。
- `User 1—N InventoryItem`、`User 1—N DailyCheckIn`、`User 1—N UserTaskProgress`。
- 签到唯一键：`(user_id, business_date)`。
- 任务进度唯一键：`(user_id, task_definition_id, period_key)`。
- 奖励幂等键唯一；领取事务中同时更新任务状态、写奖励流水、增加资源/库存。
- 聊天记录按 `conversation_id, created_at` 索引；查询时始终校验会话归属。
- `owner_id`、业务日期/周期、状态等常用过滤字段应建索引；根据实际查询和数据量再增加复合索引。

### 5.4 变更流水与一致性

签到奖励、任务奖励、喂食消耗及其宠物效果应在服务端事务内完成。建议为会改变资源或成长数据的动作保留流水（可复用 `RewardLedger` 或独立 `PetEventLedger`），包括来源、变更值、幂等键和时间。这样可排查重复请求、修正数据并支撑未来活动结算。

## 6. 全局状态设计

全局状态仅保存跨页面共享且短期需要的客户端快照；服务端仍是事实来源。首期可使用 `App` 实例中的轻量 Store/订阅机制，避免引入较重状态库，待复杂度增长再替换。

| 状态域 | 示例内容 | 生命周期/更新策略 |
|---|---|---|
| `session` | 是否已登录、会话凭证的可用状态、初始化状态 | 凭证按安全要求存储；过期时统一触发重新认证 |
| `user` | 用户 ID、昵称/头像展示信息、时区偏好 | 登录/资料接口刷新；不存微信敏感凭证 |
| `activePet` | 当前宠物摘要、属性、`state_version` | 首屏加载及宠物操作成功后，以服务端响应替换 |
| `resources` | 食物/道具数量、可展示资源余额 | 喂食和奖励结果后刷新；不在客户端作为可领取依据 |
| `dailyStatus` | 今日是否签到、待领取任务数 | 首页回前台或相关操作后刷新 |
| `ui` | 全局加载标识、当前弹层、网络错误提示 | 仅客户端临时状态，不持久化业务数据 |

### 状态管理原则

- 页面局部输入（聊天草稿、弹窗选中项、动画状态）留在页面，不进入全局 Store。
- Store 提供按业务域更新的方法，禁止页面任意修改嵌套对象；更新后可通知订阅页面。
- 登录后先取服务端摘要；页面返回前台时按需刷新关键状态，避免长时间展示过期签到/任务状态。
- 操作 API 返回最新的宠物/资源快照时直接合并或替换；若遇到版本冲突，重新拉取后提示用户重试。
- 缓存失败或网络异常要明确展示错误/重试入口，不把默认值伪装成真实业务状态。

## 7. 服务端 API 与关键业务流程

建议 API 按资源和动作组织，例如：

- `POST /session/login`：通过微信登录凭证建立服务端会话。
- `GET /me/overview`：返回用户、主宠物、资源及首页摘要。
- `POST /pets`：领养并创建宠物；服务端检查用户是否已领养。
- `POST /pets/{petId}/interactions`：记录互动并计算合法收益。
- `POST /pets/{petId}/feed`：校验库存、扣减食物、应用成长/亲密度效果。
- `GET /tasks`、`POST /tasks/{taskId}/claim`：读取任务及幂等领取奖励。
- `POST /check-ins`、`GET /check-ins`：签到及查询记录。
- `GET /chat/conversations/{id}/messages`、`POST /chat/conversations/{id}/messages`：历史读取和发送消息。

请求写操作带客户端生成的 `Idempotency-Key`；服务端同时验证用户归属、资源、频率限制和业务状态。写操作成功响应返回可直接更新页面的权威结果。

### 关键流程

1. **首次启动/领养：** 完成微信登录 → 查询用户概览 → 未领养则进入领养页 → 服务端创建宠物（并发重复请求只能成功一次）→ 返回宠物快照。
2. **互动/喂食：** 用户触发动作 → 客户端展示处理中状态 → 服务端校验次数/库存并结算 → 事务写事件、库存及宠物状态 → 返回新快照；网络重试使用同一幂等键。
3. **签到/任务领取：** 服务端基于业务时区判定日期/周期 → 检查是否已签到/已领取 → 同一事务写入领取状态和奖励流水 → 返回结果；唯一约束处理并发请求。
4. **AI 聊天：** 客户端发送消息 → 服务端验证会话归属、限流和内容策略 → 调用 AI 代理 → 保存或按策略处理消息 → 返回回复及可重试状态。模型超时与业务存储状态应清晰区分。

## 8. 非功能与产品规则建议

- **离线体验：** 可展示最近一次成功加载的只读宠物快照，并标注数据可能过期；签到、喂食和领取奖励等写操作必须等服务端确认。
- **时区与日切：** 统一明确签到业务时区和重置时间；所有客户端展示与服务端判定遵循同一规则。
- **防重复与公平性：** 互动次数、喂食频率、奖励资格由服务端限频和核验；客户端按钮禁用只用于改善体验。
- **可观测性：** 对登录、喂食、签到、领任务奖励、AI 请求记录关联请求 ID、结果和耗时；避免日志记录不必要的聊天正文或身份敏感信息。
- **隐私：** 聊天和用户数据遵循最小化收集、明确告知、可删除和合理保留；按微信平台要求接入隐私保护指引与授权流程。
- **配置发布：** 任务、奖励和物品配置需有版本、生效时间和审核/回滚流程，避免直接修改代码才能调整日常活动。

## 9. 后续扩展方案

### 9.1 换装系统

新增 `WardrobeItem`/扩展后的物品定义、`UserInventory`（如需统一库存）和 `PetEquipment`（宠物当前穿戴槽位）。每件装扮包含槽位、资源引用、解锁条件和有效期；穿戴接口校验归属、槽位冲突和持有状态。渲染层将宠物底图与装扮资源分层组合，装备数据与 UI 动画解耦。换装放入独立分包，减少首页包体积。

### 9.2 广告变现

新增服务端 `AdPlacement`、`AdRewardClaim` 等记录，将广告位、奖励规则和活动配置化。奖励只在服务端验证平台回调/可信凭据后入账，按广告展示实例设置幂等键；不能仅凭客户端“看完广告”回调发奖。首页养成闭环不应依赖广告才能完成，需预留频控、用户分群、未成年人/平台规则适配和广告失败兜底。

### 9.3 AI 聊天增强

服务端 AI Gateway 可独立扩展提示词版本、模型路由、敏感内容处理、上下文摘要、用户额度和成本监控。用户画像只传必要且可控的信息；聊天历史按产品策略截断或摘要，支持用户删除。聊天功能不可用时，其它养成能力仍可独立运行。

### 9.4 多宠物、活动和社交

- 多宠物：将当前宠物抽象为 `active_pet_id` 或独立宠物选择关系；业务接口始终明确 `pet_id`。
- 活动：任务模板使用活动周期和版本化配置，活动奖励统一进入奖励流水。
- 社交：未来引入公开展示资料与隐私权限，所有查询由服务端授权，避免暴露内部用户标识。
- 商业化/运营：奖励来源统一记录，便于区分签到、任务、活动和广告获取，并支持审计与报表。

## 10. MVP 实施优先级

1. 登录/首次领养、牧场首页和宠物资料。
2. 互动、喂食、经验/等级和亲密度的基础闭环。
3. 每日签到、任务进度与幂等奖励结算。
4. AI 聊天服务端代理及基础会话管理。
5. 埋点、错误监控、隐私流程和运营配置能力。
6. 按用户验证结果再启用库存扩展、换装分包、活动和广告。
